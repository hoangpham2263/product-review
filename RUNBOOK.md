# RUNBOOK: agent mode (Claude Code + Google Flow)

The prompt is `docs/agent-prompt.md`. One run at a time, one browser = one agent. CLI: `powershell -NoProfile -ExecutionPolicy Bypass -File src/agent.ps1 <command> -Run <run> [-Item <id>] [-File <path>]`; every command prints one JSON line `{ok,...}`; `ok:false` carries `error` (read it, do not guess).

1. `prepare`: snapshots the queue (URLs, product photos, review photos) into the run; lists the items.
2. Per item: look at the product photo(s) yourself; `context-brief` shows what to write; write the JSON (`lettered` + `sample_text` for sample customer lettering); `context -File <json>`. No web access for the product (AGENTS.md section 1-2).
   Sign wording (lettered items; the rule is AGENTS.md section 4): `sign-brief -Item <id>` prints `review_photo`, `product_photo`, `sample_text`, `sample_lines`, `taken` (wording other items already use) and `instruction` (template `prompts/sign-choice.txt`) → LOOK at both photos, choose the exact wording → `set-sign-text -Item <id> -Text "<line 1 | line 2>" -Reason "<scene> -> <wording>"`. The CLI rejects (`BAD_SIGN_TEXT` / `SIGN_TEXT_DUPLICATE` / `NOT_LETTERED` / `ALREADY_IMAGED`): empty, non-ASCII, a placeholder ("Your ...", "Name Here") or the sample words, a line count other than the sample's (when `sample_text` is known), more than 3 words on a line, the same wording as another item of the run, a missing `-Reason`. It stores `sign_text` + `sign_reason` on the item (`agent-items.json`) and logs `logs/<id>-sign-text.json`. A `sign_text` already on the scene (`references.json`, CSV column) is used as is.
Sessions: several app windows can run at once (own queue, runs, logs and port each, one source); `start-app.cmd <name>` opens one, `PR_SESSION` / `PR_WORKSPACE` name it for CLI runs. See AGENTS.md "Phiên".
3. Images in Google Flow (Playwright MCP: the person's everyday Chrome profile chosen in the app, extension mode, the person clicks Connect (or, when a Playwright extension token is saved for that profile in the app, the extension connects by itself and the RUN-NOW NOTE says so) and your tabs sit in a group named Product Review; or the tool's own Chrome `workspace/chrome-profile` when the app says so):
   1. `flow-brief` for every item: gives `aspect`, `uploads` (review photo first, product photo second) and `condensed_prompt` (with `sign_text`: the exact SIGN WORDING right after the product line, the sample words taken out of the details). A lettered item without `sign_text` returns `ok:false`, `cause:NEEDS_SIGN_TEXT`, `needs_sign_text:true` plus the sign-brief fields: set the wording, then `flow-brief` again.
   2. `browser_tabs`: browser up? One tab. A Google sign-in page = STOP (`CAUSE:LOGIN`). Open https://flow.google.com, new project, Images (Hình ảnh), aspect from `aspect`, x1.
   3. BATCH: per item upload the 2 `uploads` in that order as references, paste `condensed_prompt` in the BOTTOM prompt box (not the project name), submit. HUMAN PACING (Flow flags bursts as "unusual activity"): run `node core/flow-pace.mjs gate --tag <item id>` right BEFORE every prompt you submit; it waits the human-like time itself (5-12 s between prompts, 20-45 s after a group of 3-4, max 8 per 2 minutes); submit right after it returns; never several prompts behind one gate, never skip it. After each group wait for its results, download and register them, then go on with the next group.
   4. Per group: wait for its results, then download each original 1K image and register it before the next group. DOWNLOADS (the Downloads folder is shared by every window of this machine): around EACH download run `node core/flow-pace.mjs download-lock acquire --tag <item id>` (blocks until no other window is downloading), click download, move the NEW file at once into your own session folder (`workspace/tmp/flow-downloads/` of this session, renamed `<item id>.<ext>`), check it is the right picture (expected size, the prompt tile you submitted), then `download-lock release --tag <item id>`; never take a file you did not just download.
   5. `register-image -Item <id> -From <png>` per image (`-From`, not `-File`; `flow-brief` prints the exact command). Sign check: an item with `sign_text` needs `-SignRead "<what the sign reads, ' | ' between lines>"` (look at the image at full size; write what you see). It must equal `sign_text` (case, spacing and punctuation tolerant). `SIGN_READ_MISSING` = add it; `SIGN_TEXT_MISMATCH` (`redo:true`, `redos_left`) = not registered, make the image again in Flow with the same `condensed_prompt` and register again; only ONE redo: if the redo still reads wrong, register-image keeps the image anyway (`sign_check.kept_anyway`, the reviewer decides in Duyệt); never an error that drops the item. Tries are kept in `logs/<id>-sign-check.json` and `logs/<id>-sign-miss-<n>.*`. An item that already has an image is never run again.
   Older runs: a run folder without `agent-run.json` (`{"sign_wording":"exact"}`, written by `prepare` when it creates the run's item list) keeps the old behaviour: no NEEDS_SIGN_TEXT, Flow chooses the wording (`prompts/sign-wording-auto.txt`), `-SignRead` optional (checked when given).
4. Per item: `review-brief` (prints `prompt_file`, rating, name, image) → read `prompt_file`, write the review to a .txt file → `write-review -File <txt>` (a failure returns `{ok:false,problems,final:false,repairs_left}`: fix what it names and run it again, up to 3 repairs; the 4th draft is kept as it is, `kept_with_issue` says why; an item is never dropped for its review wording) → `finish` (uploads to the results store, adds stars/name/date; `RESULT_CONFIG` or `RESULT_UPLOAD` = item NOT done; success = status `awaiting_user_review`). The agent never touches review.json.
5. `run-summary` (prints `{ok,run,items:[{id,url,status,image,cause?}],awaiting_user_review,errors,unfinished}`), then STOP and report in Vietnamese: image paths, items waiting for approval, errors. The person approves in the app (Duyệt & xuất file).

Browser rules: `await page.bringToFront();` first in every browser_run_code_unsafe; one tab; no waitForFunction; a call over 30 s is stuck.
Errors: `[CAUSE:LOGIN|QUOTA|REFUSED|BROWSER] text` per item; no endless retry.
Never: Giữ/Bỏ, Loox export, sending anything, watermark removal via Flow, rerunning an item that has an image, signing in for the person.
Review-only run (UI Kiểu chạy = Chỉ viết review, `run-images.ps1 -ReviewOnly`): no image, no results-repo upload; reviews are written from each item's attached original review photo (an item without one fails clearly, others continue). Review-only rows show in Duyệt with the original review photo and export to Loox with an empty photo column. Agent mode (Claude + Flow) always makes images, so it is not offered for review-only.

Note: agent mode above is a separate path. The app's Viết review box can also pick Claude (`core/ai/providers/claude.ps1`, `claude -p`, Read-only, no MCP, no Chrome); it needs only the Claude CLI signed in (`PR_CLAUDE_CLI` or PATH).

## Agent backend: Claude or Antigravity

Every agent run (Flow images + reviews, Quét web, Cập nhật review, queue / prep / index) goes through the one runner `core/setup/agent-run.mjs`; Cấu hình (mục 3 Cách chạy, mục 6 Antigravity) picks the backend per window (`workspace/config/run-settings.json`: `agentBackend` claude | antigravity, `agyModel`, `agyEffort`; empty `agyModel` = agy default, the run reports the model agy says in its init event). Antigravity runs `agy -p <short task> --output-format stream-json --dangerously-skip-permissions --add-dir <tool> [--model m] [--effort e]` with cwd = a private temp folder OUTSIDE the repo (`%TEMP%/pr-agy-<run>-xxxx`, deleted when the run ends, on failure and on Dừng) that holds `prompt.md` (the same prompt, plus an ANTIGRAVITY TOOL MAP) and a project plugin `.agents/plugins/prreview/mcp_config.json` with the same Playwright MCP as the Claude path (`agy --settings` refuses `mcpServers`; global `~/.gemini/config/mcp_config.json` is never touched). agy lists the tools of that MCP only through `call_mcp_tool` (ServerName `prreview_flow`, ToolName `browser_*`, Arguments). agy's own browser_* / open_browser_url / generate_image / search_web tools, or any other MCP server, stop the run at once (one browser = one agent). No-scripts, human pacing (`flow-pace.mjs gate`), download lock and visible-tab rules are the same text for both backends. Models: `agy models` (cached 10 min, static fallback list). Chạy tiếp works for any agent. **Image run with Antigravity (picker Tạo ảnh = Antigravity)**: no Google Flow, no Chrome profile / extension / Connect, no Flow account or login check, no Playwright plugin (not written, not required), no pacing gate / download lock / project reuse. The runner uses `docs/agent-prompt-agy-image.md` instead of `agent-prompt.md`: same steps 1, 2, 4, 5; in step 3 `flow-brief` still prints condensed_prompt, the 2 uploads, aspect, sign_text, safe, and the agent calls `invoke_subagent` type_name `image-generator` once per item (generate_image: Prompt = condensed_prompt, ImagePaths = the 2 uploads in order, AspectRatio = aspect, ImageName = item id; the picture lands in `~/.gemini/antigravity-cli/brain/<conversation>/<name>_<time>.jpg`, about 1 minute per picture), copies it next to its prompt and runs `register-image -From <file>` (a jpg is converted to png) with `-SignRead` for lettered items; refused = one retry with `flow-brief -Safe`, then `[CAUSE:REFUSED]` and on. Luồng (1-4) = pictures made at once (one image-generator subagent per item of a group, same aspect together); Claude (Flow) ignores it. Only the image-generator subagent is allowed; agy's own browser/web tools or any other subagent or MCP stop the run. Run line: `Antigravity (tạo ảnh)`. Chạy tiếp works the same.

**Settings live in Cấu hình, the main window only runs** (2026-11-25): Viết review, Tạo ảnh (Codex / Claude (Flow) / Antigravity; Antigravity = imageBackend `agent` + agentBackend `antigravity`), Luồng, Chrome profile, Tài khoản Flow, token Playwright and Mở Chrome are sections of `core/setup/page.html` (mục 3 Cách chạy; the Flow-only controls show only for Claude (Flow)), saved through the same `/api/run-settings` and `/api/flow-browser*` endpoints. The main window shows one read-only summary line (click = Cấu hình) and re-reads the settings on load, focus and pageshow, so the next run and the Bắt đầu / Chạy tiếp state follow a change without a reload. Which AI runs which task is also set in mục 3: Tạo ảnh (agentBackend, image run), `scanAgent` (Quét web), `reviewsAgent` (Cập nhật review), `queueAgent` (Hàng chờ, Chuẩn bị trước, Gắn nhãn); each Claude or Antigravity (Codex cannot: the runner only starts the claude or agy CLI). `readAgentSettings(..., mode)` reads the key of the run's mode; a window saved before these keys falls back to its old agentBackend. Model and effort come from mục 5 (Claude) and mục 6 (Antigravity). The profile/account check is shared in `core/setup/flow-check.js` (preflight in the main window, live note in Cấu hình).

**Luồng at run time (Dự án popup, Quét web popup; 1-4, default = Cấu hình Luồng, remembered per window as projectThreads / scanThreads)**: Thêm vào hàng chờ, Chuẩn bị trước and Gắn nhãn kho ảnh start N light runs at once (no browser; `lightPool` in `src/mac/server.mjs`, state files `runs/prep-run[-k].*`): queue / prep split the run's products into N contiguous disjoint parts (a JSON shard file of links, `scan.ps1 queue-todo|prep-todo -OnlyFile`), index splits the library photos by a stable hash (`scene-index-todo -Shard k/n`); `queue-add` holds `queue-add.lock` from its first check to the queue write (no duplicate link, no scene taken twice), prepared.csv / scene-index.json / urls.txt+references.json keep their own locks; Dừng stops every shard, the queue order counts the files so `đã thêm x/N` stays right, and each run line names its shard. Cập nhật số review and Quét web stay ONE agent on ONE Chrome profile and read up to N pages at once in separate tabs of that session (prompt `TABS: N`, small random gaps, back off on 429, never a retry loop). Not parallel: Claude (Flow) (Flow pacing), the Antigravity image run's context / sign wording / write-review / finish steps (they share the run's items, the sign-wording uniqueness rule and the results repo, one CLI at a time), Codex image run (already uses Luồng).

## Quét web (scan mode: Claude Code + a shop website)

The prompt is `docs/scan-prompt.md` (the Quét web popup's Bắt đầu quét runs it through the same runner as agent mode, `core/setup/agent-run.mjs` mode `scan`; one agent run at a time, one browser = one agent). CLI: `powershell -NoProfile -ExecutionPolicy Bypass -File src/scan.ps1 <command> -Project <id> ...` (`-Scan` is the old name of `-Project`); every command prints one JSON line `{ok,...}`. Claude finds the menu and the products itself in the tool's OWN Chrome (Playwright MCP, no sign-in); the CLI only writes files into the web's project folder `workspace/projects/<id>/` (see "Dự án" below; older scans in `workspace/scans/` still get `used` updates).

1. `start -Site <home page> -Max <n> -Run <run>`: finds the project of that site (id = host, `dreamyvows.com` = `dreamyvows-com`) or creates it with an empty `products.csv` (header `product_url,product_image,review_images,sign_text,title,collection,used,reviews_count,reviews_checked_at`); prints the project id and how many products it already has. Then `known` lists the links already there: Claude skips them, so Max counts NEW products only.
2. Browser first (`browser_tabs`, one tab, open the site; a login wall, captcha or block page = STOP).
3. Read the main menu: product categories only (no About, Blog, policies, cart, account).
4. Per category: collect up to Max products (link, title, category, URL of the MAIN image), write a JSON array `{url,title,collection,collection_url,image_url}`, `add-many -File <json>` (or `add -Url -Title -Collection -ImageUrl|-ImageFile`). The CLI downloads and checks each image (real JPG/PNG; WebP/AVIF is re-asked as JPG with `format=jpg`; still not an image = `NEEDS_PNG`: screenshot the image element to a .png and `add -ImageFile`), skips links the project already has (`duplicate`: the row, its `used` and its review number stay) and stops a category at Max NEW products of this scan (`collection_full`). New rows start with `used = F`. Nothing is ever deleted by a scan.
5. `finish`: rows, per category, `missing_images`, `merge` (added / already_known / not_seen_this_scan) and `menu.json` with the product count of each category; then Claude reports in Vietnamese and stops.

After the scan: Nhập hàng loạt reads `products.csv` as is (Chọn file…, or "Nhập vào danh sách" in the popup). Rows with `used = T` are skipped ("bỏ qua N dòng đã dùng"); `title` and `collection` are notes. `review_images` and `sign_text` stay empty: the person chooses the review photos and the lettering. A link that finishes (Codex checkpoint, agent `finish`) sets its row to `used = T` in every scan table (`Set-ScanUsed`, `src/application/scan-store.ps1`).

## Dự án (one project per web: scan once, then only update)

Every shop is a project in `workspace/projects/<id>/`: `project.json` (id, name, site, created, updated, last_scan, last_reviews_check, max_per_collection), `menu.json` (categories with link and product count), `products.csv` (the Nhập hàng loạt table: `product_url,product_image,review_images,sign_text,title,collection,used,reviews_count,reviews_checked_at`), `images/`, `reviews.json` (the last number seen per link: count, rating, source, checked_at) and `session.json` (the running scan). The "Dự án" popup (button next to Quét web) lists the projects and shows the products of the selected one (filter by category and "Chỉ chưa dùng", used T/F toggle, review number and its date). Buttons: Quét cập nhật (the Quét web run on the project's own link: only new products are added, `used` and review numbers are kept, nothing is deleted), Cập nhật số review, Nhập vào danh sách (the used = F rows go through Nhập hàng loạt, `reviews_count` / `reviews_checked_at` are ignored on import), Mở thư mục. The Quét web popup can pick an existing project.

Thêm vào hàng chờ (button on the bottom row of the popup; the boxes "Số sản phẩm" (default 10) and "Ảnh ngữ cảnh / sản phẩm" sit in the status area above it): for the SELECTED project, takes that many products (respecting the popup's category filter and "Chỉ chưa dùng", skipping links already queued) and prepares them for image creation: the link into `workspace/urls.txt`, the project's product photo as the product image and N scene photos per product (box "Ảnh ngữ cảnh / sản phẩm", 1-4, default 2) into `workspace/reference-inputs/references.json` (entries[] -> product_url, products[] -> file + sha256 + scenes[] -> file + sha256, copies under `workspace/reference-inputs/<project>-scenes/`). Scenes box = 0 skips Claude: `/api/project/queue/direct` (`scan.ps1 queue-direct`) queues the first N products of the table (same order and filters, links already queued skipped) with only the link and the project photo. It does NOT start image creation and writes no review text/author/rating. Prompt `docs/queue-prompt.md` (mode `queue`, `/api/project/queue/run|status|stop`): Claude looks at the product photo, picks N different scenes that fit from the right library group ("Áo" apparel, "Thể thao ngoài trời" jerseys/fishing/running/cycling, "Nội thất" furniture), reports a product with no fitting scene instead of forcing one, and works to the last product. CLI (`src/scan.ps1`): `queue-todo` (products to queue), `scenes` (library groups / photos with category), `scene-get` (downloads one library photo, md5 checked, prints its path and used_count), `queue-add -Url -Group -SceneNames a,b[,c,d]` (1-4 different photos) (verifies sha256, writes the entry and the urls.txt line; never changes an existing entry or link). Scene checks use a perceptual hash (16x16 dHash, `src/infrastructure/image-phash.ps1`, cache `workspace/source-photos/phash.json`; same picture re-saved/resized = distance 0-6 of 256, different photos 99+, limit 20): `scenes -Group g [-Category c] [-Prefetch]` adds `used_count` (queue + last 5 runs), `dup_of` (first visually identical library photo) and `checked` per photo and lists unused photos first in a stable shuffled order; `queue-add` rejects `[CAUSE:SCENE_DUPLICATE]` (two scenes of one product look the same) and `[CAUSE:SCENE_REUSED]` (a scene already used by another product in the queue or the last 5 runs; `-AllowReuse` overrides). The prompt tells Claude: products come grouped (`queue-todo -Grouped -Sheet`, one product sheet per group), scenes come from `scene-candidates` contact sheets (tag index, see "Gắn nhãn kho ảnh"), never reuse a scene across products of a batch, spread the picks; the report ends with "X distinct scenes / Y scene slots". When the run ends the main window list reloads so the result can be checked (Xem / sửa).

### Chuẩn bị trước (prep mode) and the instant queue

The popup has two SEPARATE groups, each with its own numbers (remembered per session in `config/run-settings.json`: `queueCount`, `queueScenes`, `prepCount`, `prepScenes`): Thêm vào hàng chờ (Số sản phẩm 1-200, default 10; Ảnh ngữ cảnh / sản phẩm 1-4, default 2) and Chuẩn bị trước (Số sản phẩm, 0 = all remaining, default 50; Ảnh ngữ cảnh / sản phẩm, default 4 so the queue can take any 1-4 from the same rows). The footer line says how many prepared rows the queue can use with its scene number: `Chuẩn bị trước: X sẵn sàng (≥ S ảnh) · Y chưa chuẩn bị · Z đã ở hàng chờ` (`prep-status -SceneCount S` -> `ready_usable`).

Picking scenes at queue time is slow, so it can be done IN ADVANCE: "Chuẩn bị trước" (button next to Thêm vào hàng chờ in the popup; `POST /api/project/prep/run`, `docs/prep-prompt.md`, runner mode `prep`) lets Claude go through the products of the selected project (category / "Chỉ chưa dùng" filters) that are not prepared yet and store S different fitting scenes per product in `workspace/projects/<id>/prepared.csv` (columns `product_url,group,scenes,scene_sha256,scene_count,prepared_at,status,consumed_at,consumed_by`; status `ready` | `skipped:no-fit` | `consumed`; shared by every session; one row per product the moment it is picked, written under a file lock). It never touches `urls.txt` / `references.json`. The prep and queue runs use the LIGHT runner (own state `workspace/runs/prep-run.json`, own Dừng, no browser and no Chrome profile) and may run while Bắt đầu runs; two light runs at once are refused.

Speed (2026-11-21): a prep run on dreamyvows-com (126 neon signs) took 9+ minutes and 60+ turns before its first saved product, because Claude opened every candidate scene with Read (>= 6 per product, across groups). Now Claude looks at numbered CONTACT SHEETS (one Read = up to 20 photos) and only at scenes whose tags (scene index, below) match the product type; every safety check stays (SCENE_DUPLICATE, SCENE_REUSED, sha256, prepared.csv states, locks). Claude still judges every fit by looking: the tags only narrow the list, no code picks a scene.

1. `prep-status` (counts) and `prep-todo -Grouped -Sheet -Limit 40` (products not queued and not prepared, grouped by kind: `groups[]` = key (collection, else a type word of the title), products with `n`, and `sheet` = one contact sheet of the group's product photos; chunks of 20; call again when done). The checkbox "Thử lại sản phẩm đã bỏ qua" (remembered per session, `prepRetrySkipped`) passes `retry skipped (no-fit) products: T` and `prep-todo -RetrySkipped` lists the `skipped:no-fit` products again; `prep-add` replaces their row (or refreshes it on a new -Skip); ready / consumed rows are never touched. The footer shows `· N đã bỏ qua`.
2. Library index: `scene-index-status`; a needed group with untagged photos is tagged first (as in "Gắn nhãn kho ảnh").
3. Per group of products: Read the product sheet once and decide the type; `scene-candidates -Group "<g>" -Fits "<type>" [-Setting a,b] -Limit S x products + 8` (max 60) lists unused, non-duplicate indexed scenes ranked by tag match with numbered `sheets` (20 each); Read every sheet and assign S different fitting scenes per product (no duplicate look, no reuse across products, all S from one library group).
4. `prep-add -Url <link> -Group "<group>" -SceneNames "a,b" -SceneCount S` per product right after its assignment (store as you go, the queue can take it at once) (or `-Skip -Reason "no-fit: ..."`); ALREADY_PREPARED / ALREADY_QUEUED skip; SCENE_DUPLICATE / SCENE_REUSED take another scene from a sheet already seen. Keep working until everything is prepared or the number in OPTIONS is reached.
5. `prep-status`, then report in Vietnamese (with the number of sheets read) and stop.

Images opened per product (throwaway test 2026-11-21, 4 products x 3 scenes, 23 candidates): before >= 7 Reads per product (1 product photo + 6 scenes); after 1 product sheet per group + 2 candidate sheets for the group = 3 Reads for 4 products (0.75 per product); with full groups of 20 products x 4 scenes it is 1 + 5 sheets = 6 Reads for 20 products (0.3 per product). Tagging is a one-time cost: about 1 sheet per 20 library photos, then only new photos.

### Gắn nhãn kho ảnh (index mode: the scene library tag index)

`workspace/source-photos/scene-index.json` (shared by every project and session, written only by `scan.ps1 scene-index-add` / `scene-index-todo` under `scene-index.json.lock`, atomic write): per library photo `<group>/<name>`: group, name, category, md5, sha256, phash (computed by the CLI) and the tags Claude wrote after looking at the photo ONCE on a contact sheet: `setting` (bedroom, kids room, bar counter, cafe window, wedding backdrop, living room, dining room, office, outdoor, studio ...), `people` (bool), `light` (day | night | warm), `wall_space` (bool), `fits` (product types it suits, free text list), `note`, `usable` (false = no product could use it); `dup_of` for a photo visually identical to one already indexed (no tags). An entry whose md5 no longer matches the library manifest counts as untagged. The Dự án popup shows `Kho ảnh: N ảnh · M đã gắn nhãn · K chưa gắn nhãn` (`GET /api/library/index` -> `scene-index-status`) and the button "Gắn nhãn kho ảnh" (`POST /api/library/index/run`, `docs/index-prompt.md`, runner mode `index` on the LIGHT runner: no browser, runs while Bắt đầu runs; one light run per window; one index run per machine via the lock `library/scene-index`; Dừng = `POST /api/library/index/stop`).

1. `scene-index-status` (photos / indexed per enabled group).
2. `scene-index-todo -Group "<g>" [-Category c] -Limit 20` (max 24): the next untagged photos, downloaded and hashed; visual copies of indexed photos are recorded as `dup_of` and left out; prints `sheet` (one numbered contact sheet, in this session's `tmp/contact-sheets/`) and `photos` (n -> name).
3. Claude Reads the sheet once and writes one JSON item per number.
4. `scene-index-add -File <json>`: each item validated (photo exists, setting / light / yes-no / fits), the valid ones written at once, the others returned in `errors`. Back to 2 until every group (or the group / number in OPTIONS) is done.
5. `scene-index-status`, report in Vietnamese, stop.

Other CLI: `contact-sheet -Group g -Names a,b,c | -Files p1,p2 [-Cols 4] [-Out x.png]` (any photos tiled ~300 px with a big number each, 20 per sheet, legend number -> name also saved as `<png>.json`); `queue-todo -Grouped -Sheet` (the queue prompt's grouped list, same shape as `prep-todo -Grouped`). Contact sheets come from `src/infrastructure/contact-sheet.ps1` (System.Drawing, the same library as the perceptual hash). Tests can point the library at a copy with `PR_LIBRARY_DIR` (+ `PR_SOURCES_URL`, `PR_SCAN_OUT`, `PR_WORKSPACE`).

`Thêm vào hàng chờ` first runs `queue-from-prepared -Project <id> -Limit N [-SceneCount S] [-Collection] [-UnusedOnly]` WITHOUT an agent: it queues up to N ready rows (re-validating that the scene files exist, sha256 matches and the scenes are not used by another product; a row that no longer validates is dropped back to "not prepared"; a queued row becomes `consumed`). The shortfall M is NEVER dropped: it becomes the session's one pending order (`GET /api/project/queue/order`, the popup shows `Hàng chờ: đã thêm X/N (Y từ kho chuẩn bị, Z Claude đang chọn thêm)`). When the light runner is free the Claude queue run starts at once for M; while a Chuẩn bị trước run is active the order pulls the new prepared rows (each time prepared.csv changes, at least every 15 s) and, when that run ends, starts the Claude queue run for exactly the remaining count. Nothing left to queue (all used or queued) ends with a clear message instead of starting Claude. Dừng cancels the order. Rows prepared with fewer scenes than S are top-ups for the queue run (`queue-todo -TopUp -SceneCount S`: keep their scenes, pick only the missing ones); `queue-add` records its picks in prepared.csv as consumed. The queue writes (`Add-QueueEntry`, `Save-ManualMapEntry`, `Remove-FromQueue`) go through one OS mutex per session workspace (`Use-QueueMutex`), so a running batch, the app and queue-from-prepared never lose each other's entry. New CLI: `prep-todo`, `prep-add`, `prep-status`, `queue-from-prepared`.

CLI (`src/scan.ps1`, one JSON line each): `projects`; `project -Project <id>` (summary + menu); `set-used -Project <id> -Url <u> -Used T|F`; `known` / `set-menu -File <json>` (scan helpers); `reviews-todo -Project <id> [-Limit n]` (links to read, never checked first); `set-reviews -Project <id> -Url <u> -Count <n> [-Rating <x>] [-Source <where>]` (stores the number Claude reports and the time; unknown link = error). A link that finishes sets its row to `used = T` in every project table (`Set-ScanUsed`).

### Cập nhật số review (reviews mode, READ ONLY)

The prompt is `docs/reviews-count-prompt.md` (runner mode `reviews`, `POST /api/project/reviews/run` {project}, `GET /api/project/reviews/status`, `POST /api/project/reviews/stop`; one agent run at a time, shared with Flow and Quét web). No code finds or parses review numbers: Claude opens each link in the tool's OWN Chrome, reads the number the page itself shows (whatever widget or wording shows it) and records it with `set-reviews`.

1. `reviews-todo` lists the links (never checked first).
2. Browser first (`browser_tabs`, one tab; no Playwright MCP = STOP).
3. Per link: open it, dismiss a cookie banner with one click, read the review number on the page (scroll if it helps; "No reviews yet" = 0; no review information anywhere, or a number that is not clearly this product's = do not guess, note the link for the report and go on to the next link; one doubtful link never stops the run).
4. `set-reviews -Url <link> -Count <n> [-Rating <x>] [-Source "<where>"]`; a failed call is retried once. Keep working until every link is done: a headless run ends the moment Claude writes a message without a tool call, so no progress message, partial report or question before the last link (a 2026-11-18 run stopped after 4 of 346 links because the prompt asked for a progress line).
5. `project` shows what is stored; Claude reports in Vietnamese and stops.

STOP IF a login wall, captcha or block page. NEVER write, submit, edit, delete or vote on a review, fill a form, sign in, guess a number or set a target; the project stores only the observed count (no target, no "missing" number).
