# Agent prompt (Claude Code drives Google Flow and writes the reviews)

The only source of the prompt: the app ("Claude (Flow)" in Tạo ảnh: Bắt đầu runs it, Copy prompt copies it) and `GET /api/agent/prompt` read the `text` block below. Placeholders: `{{TOOL}}` = this tool's folder, `{{RUN}}` = the run id, `{{OPTIONS}}` = this run's options (or "defaults"). Fixed template: TASK, OPTIONS, TOOL, STEPS (numbered, 1:1 with RUNBOOK.md), STOP IF, NEVER. With Antigravity as the agent (Cấu hình mục 3 và 6) the runner only replaces "agent: Claude Code" and puts an ANTIGRAVITY TOOL MAP in front (Bash = run_command, Read = view_file, browser_* = call_mcp_tool ServerName prreview_flow); this text stays one source. Details live in RUNBOOK.md; change a step there and keep its line here in sync.

```text
TASK: Product Review — create images in Google Flow and write the reviews — agent: Claude Code
RUN: {{RUN}}
OPTIONS: {{OPTIONS}}
TOOL: {{TOOL}}
STEPS (follow RUNBOOK.md, in order, do not skip; every command prints one JSON line {ok,...}; CLI = powershell -NoProfile -ExecutionPolicy Bypass -File src/agent.ps1 <command> -Run {{RUN}} [-Item <id>]):
1. Setup: cd {{TOOL}}; read AGENTS.md (sections 0, 1, 5, 8) (open RUNBOOK.md only if a step below is unclear, it is long); CLI prepare (snapshots the queue into this run and lists the items).
2. Context, per item (one at a time), GROUP BY GROUP (the next group of up to 4 items, never all items first: Flow must get its first prompt early; while Flow renders a submitted group, do this step for the NEXT group, it needs no Flow): look at the product photo(s) of the item; CLI context-brief -Item <id> (when it answers cached:true, this product photo already has its context from an earlier item or run: run `context -Item <id> -Cached` and do NOT look at the photo again; otherwise as follows); write the JSON it asks for (also `custom_logo` true + `logo_placeholder` when the product has a buyer-logo area with replaceable sample branding (STEP 3C, e.g. the chest mark of a custom polo): the image replaces that whole sample logo with an INVENTED brand name (flow-brief prints it as logo_name); `lettered` true + `sample_text` = EVERY line of words on the sign, fixed design words included (they are replaced too), " | " between lines, when the product photo shows sample customer lettering such as "Your Name" / "YOUR LOGO"); CLI context -Item <id> -File <json>. SIGN WORDING (lettered items only; YOU choose it, not Flow): CLI sign-brief -Item <id>; LOOK at its review_photo (the scene) and product_photo; choose the exact new wording by its `instruction` (fits the place/occasion of the scene, short correctly spelled English, same number of lines as the sample, max 3 words per line, no real brand/famous name, never the placeholder, different from the other items of this run); CLI set-sign-text -Item <id> -Text "<line 1 | line 2>" -Reason "<scene> -> <wording>" (ok:false = read the error, choose again).
3. Images: CLI flow-brief -Item <id> for every item (cause NEEDS_SIGN_TEXT = a lettered item without wording: do the step 2 SIGN WORDING for it, then flow-brief again). BATCH: for each item upload its 2 `uploads` files as references in that order (review photo first, product photo second), paste `condensed_prompt` into the BOTTOM prompt box (not the project-name field), submit; submit the items GROUP BY GROUP with HUMAN PACING (Flow flags bursts as "unusual activity"): run `node core/flow-pace.mjs gate --tag <item id>` right BEFORE every prompt you submit; it waits the human-like time itself (5-12 s between prompts, 20-45 s after a group of 3-4, max 8 per 2 minutes); submit right after it returns; never several prompts behind one gate, never skip it. KEEP UP TO TWO GROUPS IN FLIGHT (at most 6 prompts rendering at once; never wait idle for a render): a group = 2-3 items of the SAME aspect (the aspect chip changes only when the aspect changes). The moment a group is submitted and the gate lets the next prompt through (the gate before EVERY prompt, its limits unchanged, one tab, no bursts, no extra speed-up), submit the next group WITHOUT waiting for the previous group's renders. Then work in a loop of SINGLE steps (no scripts, no loops written for me): look at the Flow results; for each submitted prompt that has finished, download it (download-lock around each download), check it is the right item (the prompt tile and the references shown in Flow are that item's; keep a short note 'item id -> submitted at' and use the item id as the gate --tag so a download always maps to the right item), then register-image it (sign check as below); submit the next group whenever fewer than 2 groups are rendering; use the waiting time for step 2 of the next items (it needs no Flow), never for anything that needs Flow at the same time. SAFETY (strict): on ANY Flow warning, "unusual activity", limit / quota or login message, a burst of refusals, or when 3 prompts in a row fail: STOP submitting at once, finish downloading what is already done, report the CAUSE and never retry in a loop; the ONE ITEM REFUSED rule below is unchanged. Then download each image as the original 1K size (DOWNLOADS (the Downloads folder is shared by every window of this machine): around EACH download run `node core/flow-pace.mjs download-lock acquire --tag <item id>` (blocks until no other window is downloading), click download, move the NEW file at once into your own session folder (`workspace/tmp/flow-downloads/` of this session, renamed `<item id>.<ext>`), check it is the right picture (expected size, the prompt tile you submitted), then `download-lock release --tag <item id>`; never take a file you did not just download.); CLI register-image -Item <id> -From <png> for each one (flow-brief prints the exact command). SIGN CHECK (items with `sign_text`, flow-brief adds -SignRead to the command): LOOK at the image at full size, read what the sign actually says and pass it as -SignRead "<line 1 | line 2>" (what you SEE, never copied from sign_text); it must equal sign_text (case/spacing tolerant). Cause SIGN_TEXT_MISMATCH = not registered: make that item's image again in Flow with the same condensed_prompt and register again (ONE redo only; if the redo is still wrong, register-image keeps the image anyway, go on).
4. Reviews, per item: CLI review-brief -Item <id> (prints prompt_file, rating, name, image); read prompt_file and write the review as a .txt file; CLI write-review -Item <id> -File <txt> (ok:false + problems: fix exactly what it names (it quotes a reused phrase) and run write-review again, up to 3 repairs; the 4th draft is kept as it is, so an item is never dropped for its review wording); CLI finish -Item <id> (uploads the result; CAUSE:RESULT_CONFIG or CAUSE:RESULT_UPLOAD = item NOT done, report it).
5. Report: CLI run-summary (items, awaiting_user_review, errors, unfinished); then STOP. Tell me in Vietnamese: image paths, how many items wait for my approval (Chờ duyệt), errors per item.
FLOW PROJECT (set up ONCE, then reuse): run `node core/flow-pace.mjs project get`. If it returns a url, open THAT project directly (its settings Hình ảnh / Nano Banana 2.1 / x1 are kept; check the chip, only the aspect may need a change) instead of creating a new one. Only when there is no saved url, or it fails to open, create a project, set it up once, then run `node core/flow-pace.mjs project set --url <the project url>`. ALL ITEMS: the run has MANY items (run-summary lists them): process EVERY item, group after group, until CLI run-summary shows no item with status needs_image (an item you gave up on with [CAUSE:REFUSED] counts as handled). Never stop after one group, never write a final summary and never say the run is complete before that; if only some items are done, keep going with the next group. NEVER trust an empty list: `prepare` lists EVERY unfinished item of the run (new:false for the ones already prepared by the app or an earlier call), so an empty `items` list alone never means "nothing to do"; before you ever say the queue is empty or the run is complete, check CLI run-summary (every item with status needs_image still needs its image) and agent-items.json.

STATUS LINES (the person reads them in the app while the run goes): one short Vietnamese sentence, item first, then the result, e.g. "Mục 035: đã gửi Flow", "Mục 035: ảnh đạt, chữ Shear Studio", "Mục 035: Flow từ chối, thử lại mô tả an toàn", "Mục 035: bỏ qua (Flow từ chối 2 lần)", "Mục 013: lỗi cảnh, bỏ qua". No English, no internal jargon (no CLI names, no CAUSE codes) in these lines.
```
